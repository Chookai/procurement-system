What happens in each phase

Phase 1 · Local Git

Create a baseline we can inspect.

  • Initialize main using your configured Git identity.
  • Commit the existing implementation, tests, designs, canonical lessons, Markdown tickets and sanitized evidence.
  • Exclude real credentials, generated signing keys, dependencies, caches and compiled mirrors.
  • Future changes use focused commits on short feature branches.

Evidence: a local baseline commit and clean working tree. Earlier work stays one baseline; we do not invent past commits.

Phase 2 · GitHub Actions

Catch regressions on every PR.

  • React: locked install, TypeScript and production build.
  • FastAPI: locked Python environment and real PostgreSQL tests.
  • Docs: rebuild the ticket/learning pages and check local links.
  • Save the app build and JUnit test report as short-lived artifacts.

Boundary: no OpenRouter/Azure credentials and no paid model calls in PR CI. Hosted success is unverified until a first run.

Phase 3 · Repository connection

Activate the prepared workflow.

  • Repository selected: Chookai/procurement-system (public).
  • Connect the remote and push the baseline.
  • Inspect the first Actions results and fix runner-specific failures.
  • Require the two CI checks before merging changes to main.

Still needed: the GitHub workflow permission grant. Remote is connected to Chookai/procurement-system; the first push is pending.

Phase 4 · Azure CD proposal

Deploy a tested version to a real environment.

  • Finish ingestion, retrieval and RAG evaluation gates first.
  • Define Azure hosting, database, Blob, application identity and runtime configuration.
  • Add packaging, migrations, HTTPS, smoke checks and rollback.
  • Use OIDC for Azure access; staging first, production through an explicit release gate.

Still needed: Azure destination and identity. No deployment workflow or cloud resources are provisioned. Foundry remains deferred.

Verified locally: 75 backend tests passed from a clean export without your .env. Linux frontend/prototype builds, TypeScript, generated documentation links and Actions YAML validation passed. Read the local verification record. The first hosted GitHub run remains pending.

General → Azure

Generally: CI checks a change. CD releases a tested version to a configured environment. A commit, a passing CI run and a production deployment are three different pieces of evidence.

For our Azure direction: GitHub Actions can be the delivery runner while the API/worker, database and Blob live on Azure. OIDC can provide Azure access without a stored long-lived deployment password. The actual federation and environment claims depend on the repository we connect. GitHub’s Azure OIDC guide.

Agent workflow: Plan/spec/tickets here → Kilo Desktop implements → verification here. Review the accepted role split and manual handoff templates.

Inspect the concrete files

  • CI workflow — two jobs, fixed action commits, read-only repository permission.
  • Detailed execution plan — commands, exclusions, coverage and deployment prerequisites.
  • Git exclusions — local credentials and disposable files stay local.
  • Tracked-file guard — checks staged content without printing credential values.
