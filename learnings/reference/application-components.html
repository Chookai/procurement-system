Actual component shape: register, detail and login markup are currently inside App; they are not separate Register.tsx or Login.tsx modules. We can extract them later when useful.

createRoot → <App>
  state: auth, records, selected, form, busy, error
  when signed out → login form
  when signed in

    when creating/editing → <RequisitionForm>

Not every text input has its own useState in this form: ordinary input values are read using FormData. Selected kind and line count are React state. useEffect performs operations such as session restoration and fetching records after identity changes; useRef holds command-key and current-identity bookkeeping without itself requesting a render.

FastAPI: route, contract, identity, rules and storage

A route associates a method/path with a handler. A Pydantic body model provides parsing and validation. Routing basics · Body models. The file split below is our convention, not a FastAPI requirement.

Our field example: Line.quantity in contracts.py is a Decimal with gt=0, an upper limit and two-decimal precision. Transition.expected_version requires a positive integer. Neither check proves that an approver may act on the current stored PR; that is a workflow decision.

Persistence detail: most PR fields currently live together in the table’s data JSONB column. Owner, status, version and total have their own columns. Adding a request field therefore does not always require a new SQL column, although stored data, reads, compatibility and tests still need consideration.

One request across both sides

RequisitionForm.save()       collect fields
  → App.save() → api()       POST JSON + command headers
  → Vite /api proxy         local development forwarding
  → app.py route            connect HTTP request to handler/dependencies
  → contracts.py models     validate fields
  → identity.py             establish the active account
  → workflow.command()      enforce action, version and retry rules
  → database.connect()      transaction; commit or roll back
  → PostgreSQL              persist PR + audit + command result
  → JSON response
  → refresh() → setRecords()
  → React renders the saved result

This is a responsibility map, not an exact ordering guarantee between FastAPI’s body validation and dependencies. The implemented walkthrough provides the detailed approval path.

Where would I make a change?

  • Rename a button: JSX in main.tsx. Adjust its spacing in style.css.
  • Add a required field: request model, form collection, frontend types/rendering and tests; check stored-data compatibility too.
  • Change who may approve: backend identity/permission and workflow rules, then UI affordances and negative API tests.
  • Change what is stored: review the database structure and data format; add a migration where needed.

General → Azure

Proposed mapping for our project: built React assets → Static Web Apps; FastAPI process → Container Apps; PostgreSQL → Azure Database for PostgreSQL. The browser still calls an API, fields are still validated on the server, and workflow rules still protect writes. Hosting and production identity/network/security details require separate implementation. No Azure resources are deployed by this lesson.

Small working glossary

Component / JSX
A React UI building block / the markup-like syntax used to describe its output.
Props / state
Inputs passed to a component / memory owned by a component.
Route / handler
A method-and-path mapping / the Python function that processes it.
Contract / validation
The expected input structure and constraints / checking a value against them.
Middleware / dependency
Request-wide processing around handlers / reusable inputs or checks resolved for a route.
Authentication / authorization
Establishing who the caller is / deciding what that caller may do.
Migration / transaction
A versioned database-structure change / a group of operations committed or rolled back together.
Frontend type / runtime validator
A TypeScript development-time check / executable checking of actual incoming data. Type annotations are erased; our handwritten PR type is not runtime response validation.

Business terms such as PR, PO and goods receipt follow the project glossary.
