Find the failing layer.

When the agent gives a bad procurement answer, know which part to inspect before changing the prompt or the model.

Interactive teaching example · No real RAG run
Your win: distinguish a retrieval failure, an answer failure and an authorization failure using one familiar transaction.

One case, one expected outcome

Our synthetic PO orders 10 units at MYR 200 each. The latest goods receipt accepts 6 units. A supplier invoice for MYR 1,200 has been reviewed.

The user asks: “How many units are outstanding, and is this paid?”

Expected answer: 4 units remain outstanding. The invoice is reviewed; payment is outside this milestone, so no payment status is established.
Production rule for this project: exact quantities come from authorized structured records. Document citations explain the supporting PO and GR evidence. Invoice review does not establish payment.

1. The general explanation

RAG retrieves evidence and gives it to a model to help answer a question. Evaluate the evidence search separately from the final answer: this distinction helps locate the source of an error. Microsoft’s process and system evaluation guidance uses this separation.

Find allowed evidence → Answer with support → Enforce action permissions
  • Retrieval: did the system find the current PO and GR evidence this identity may access? Missing the GR can leave the model without evidence for accepted quantity.
  • Answer: with the correct evidence and structured facts available, did it report 4 outstanding, cite support and avoid inventing a payment?
  • Authorization: did the backend prevent actions this user cannot take? A correct explanation never gives an agent permission to approve a PR.

These are project-specific checks. Ingestion is an earlier checkpoint: a GR that was never extracted correctly can cause a later retrieval failure. Inspect source extraction and indexing before tuning search.

Apply this to our first real run

Keep one row per case with the user identity, record snapshot, expected passages, exact expected facts, allowed actions, retrieved passages, answer and tool results. Then we can tell whether a failed case needs an ingestion fix, a search change, an answer change or a permission fix.
