An issued PO is a snapshot.

Know why the approved estimate and issued commercial terms are separate records.

Your win: explain which value is authoritative for the PR estimate and which belongs to the issued supplier order.

Approved PR

10 pump seals × MYR 200

Estimate: MYR 2,000

Aina requested; Ben approved.

Issued PO

10 pump seals × MYR 190

Issued total: MYR 1,900

Chloe confirmed the supplier and issued.

Both totals are correct for their own record. Issuing the PO does not rewrite the approved estimate. The PO stores a copy of the confirmed scope, prices, supplier, delivery terms and approved PR version.

Follow the extension in the code

React: PurchaseOrderForm.tsx
  collect supplier, final unit prices and delivery terms
  → App.issueOrder() → api()
FastAPI: app.py
  POST /requisitions/{id}/purchase-order
  → contracts.py: IssuePurchaseOrder validates fields
  → identity + workflow.command("issue_po")
    buyer only; approved PR; correct version
    reject an existing PO or increased line price
    copy approved fields and apply confirmed prices
PostgreSQL: migration 002 + one transaction
  INSERT immutable purchase order
  increment linked PR version
  append audit event + save retry result
React: refresh and display saved PO snapshot

Body validation and identity dependencies protect the route; the sketch groups their responsibilities rather than promising an exact order between independent checks. Quantities and scope come from the approved PR, not editable PO form fields.

Why one transaction matters

The PO, linked PR version, audit event and retry response must succeed together. PostgreSQL transactions commit a group of changes together or roll it back. PostgreSQL transaction tutorial.

Two different issue commands compete for the same PR row lock; after one commits, the other sees a stale version or an already-issued order. A retry using the same command key and body returns its saved result instead.
