Approval is not issuance.

Identify which record is authoritative while a PO change is being reviewed.

Your win: explain why approving MYR 2,640 does not immediately replace an issued MYR 1,900 order.

Generally: two records, two jobs

Current issued PO

10 seals × MYR 190

MYR 1,900 · Revision 1

This remains the issued commitment while a change is pending or approved.

Proposed replacement

12 upgraded seals × MYR 220

MYR 2,640 · Awaiting Ben

Chloe gives the complete new terms and a reason. Ben must review them.

Click through the boundary

Chloe proposes MYR 2,640

Current PO: MYR 1,900. Ben can approve or return the proposal with a reason. Chloe cannot issue unapproved changes.

Ben approves MYR 2,640

Current PO: MYR 1,900. Approval authorizes these exact proposed terms; it does not issue them.

Chloe issues the approved proposal

Current PO: MYR 2,640 · Revision 2. Revision 1 stays readable at MYR 1,900. The original PR estimate remains MYR 2,000.

A returned proposal remains in history. Chloe submits a new proposal for another review. In this small implementation, every proposed change receives approval; there is no automatic bypass for a smaller value.

Inspect the actual code

React: POReview.tsx
  show current issuance + proposal + issued history
  Approve / Return / Issue callback → App.api()
FastAPI: app.py + contracts.py
  authenticate and validate command fields
workflow.py: command() → proposal_command()
  role + PR version + proposal identity + state checks
  issue only the exact approved snapshot
PostgreSQL: migration 003
  append revision; mark proposal issued
  increment PR version + append audit + save retry result
  commit together, or roll everything back

A transaction prevents a failure from leaving a new revision without its audit entry or with a proposal still marked approved. PostgreSQL 17: Transactions. Our failure-injection test deliberately rejects the audit write and checks that issuance also rolls back.

Azure-specific: same authority boundary

Azure Database for PostgreSQL is a managed PostgreSQL service. In our proposed Azure deployment it would host the workflow tables. Our FastAPI rules and database transaction would still enforce approval and issuance; hosting the database on Azure does not create procurement permissions.

Current implementation: local PostgreSQL and signed demo sessions. Future Azure identity integration must supply a verified user to the same authorization checks. Foundry remains deferred. This is a mapping proposal, not deployed infrastructure.
